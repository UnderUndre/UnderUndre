# 📡 Trigger Playbook (v2.0 — Discovery-First)

**Назначение:** связать наблюдаемый сигнал (OSINT) с гипотезой боли и первым сообщением (L1 Trigger Note), не продавая решение до диагностики.  
**Продукт воронки:** `SpecKit Discovery` ($350–$490, Product 0, 4-Level Gate).  
**Эпистемический фундамент:** веса улик L1–L5 из `speckit.workaround-audit.md` (OSINT = L4, W = 0.3, потолок: Direction ≤ 60%, Magnitude ≤ 20%); Alt 0 (Healthy Growth); Blindfold Test.

> **Версия:** 2.1 (2026-11-05) — v2.0: переход от «диагноз-утверждения + ранняя продажа» к «сигнал → возможные гипотезы → вопрос-выбор», триггеры #6–#12, полевая структура. **v2.1:** Raw Touch Log (плоский лог касаний вместо агрегата), Trigger #13 New Executive (Job Change), Tool Ladder (Sales Navigator → Clay → CRM) с гейтами.

---

## 🧭 Правила Письма (Writing Rules — нарушение = заметка не отправляется)

1. **Сигнал ≠ диагноз.** Вакансия, репост, смена инструмента — это **сигнал**, а не причина. Одна и та же вакансия стоит за 3–5 разными болями. Формулировка — всегда «часто за этим стоит…», минимум **2–3 сценария-гипотезы**, никогда одиночное утверждение с цифрами.
2. **OSINT-потолок.** Из вакансии запрещено утверждать величину потерь («съедает 25+ ч/нед», «переплата $15k/год»). Числа появляются только после L1/L2 улик (логи, скриншоты, shadowing) внутри платного Discovery.
3. **В L1 не продаётся решение.** Ни бот, ни FOSS-офис, ни спринт. Первое касание продаёт ровно одну вещь: **готовность проверить, какой сценарий ваш**. Решение (Build / Buy / SOP / Do Nothing) — вердикт Discovery, а не аутрича.
4. **CTA по трению (минимум трения — лучший):**
   - Лучший: **вопрос-выбор сценария** («какой из трёх у вас?») — ответить можно одной строкой.
   - Средний: оффер короткой проверки (60-сек разбор, 3 вопроса).
   - Худший: «давайте созвонимся» — используется последним.
5. **Alt 0 проверяется всегда.** Перед отправкой спроси себя: «а вдруг у них просто быстрый рост и всё нормально?» Если заметка звучит так, будто у клиента точно проблема — переписать.
6. **Blindfold Test.** Заметка должна быть честной даже если мне запрещено продавать реализацию. Если крючок работает только при продаже бота — это не триггер, это спам.
7. **Red Flags = стоп-слово.** Любой флаг из карточки триггера (или ABORT-триггеры аудита: нет P&L-байера, отказ от телеметрии, нулевой спрос) — касание не отправляется, кандидат в архив.

## 🗂 Карточки Триггеров

Структура каждой карточки:

- **Signal** — что именно наблюдается (OSINT, где смотреть).
- **Possible Hypotheses** — 2–4 возможных причины, включая Alt 0.
- **Evidence Needed** — какая улика подтвердит/убьёт каждую гипотезу.
- **Mini Audit Angle** — под каким углом входит SpecKit Discovery.
- **Discovery Angle** — вопрос для разговора после ответа.
- **Red Flags** — когда сигнал ложный / не лезем.
- **Copy-Paste Trigger Note** — готовое первое сообщение.

### Trigger #1. WhatsApp Trap

- **Signal:** Вакансия администратора / Booking Lead / оператора чата открытая **>30 дней**, повторный пост; ключевые слова «переписка с клиентами», «запись клиентов», «ведение чатов». Источники: hh, LinkedIn Jobs, Telegram-каналы вакансий.
- **Possible Hypotheses:**
  - **H1 (перегрузка переписки):** приём записи и консультации вручную в мессенджерах съедает часы персонала.
  - **H2 (потерянные лиды):** записи теряются между чатами, клиенты не дожидаются ответа.
  - **H3 (Alt 0, рост):** бизнес растёт так быстро, что просто нужен ещё один человек — процесс при этом работает.
  - **H4 (дешёвый труд):** регион с дешёвым трудом — найм админа дешевле любой автоматизации.
- **Evidence Needed:** L1 — экспорт чата/CRM (время первого ответа, доля пропущенных); L2 — 15-мин shadowing одного администратора; L3 — оценка часов администратора (с хэйркатом 50%).
- **Mini Audit Angle:** TDABC по рутине приёма записи + Change Capacity (готовы ли вообще к смене процесса) + Via Negativa: если найм админа дешевле Discovery-софта — честно сказать.
- **Discovery Angle:** *«Какой из трёх сценариев ближе: перегрузка, потерянные записи, или просто быстрый рост — и сколько человек сейчас держат переписку?»*
- **Red Flags:** vacancy rate ниже рынка (найм дёшев и быстро закрывается); нет выделенного человека на чаты (сигнал пустой); экономика бизнеса не тянет даже $350.
- **Copy-Paste Trigger Note:**
> «Здравствуйте, [имя]. Вижу, у вас открыта вакансия администратора на запись клиентов ([источник], с [дата]).
> Часто за такими вакансиями стоит одна из трёх ситуаций: переписка в мессенджерах съедает часы персонала, записи теряются между чатами, или просто быстрый рост и нужен ещё человек.
> Какой из сценариев у вас? Если первые два — могу за 15 минут показать, как это проверяется цифрами, прежде чем что-то менять.»

### Trigger #2. FOSS / SaaS Tax

- **Signal:** Вакансия DevOps / SysAdmin / IT-поддержки в компании, чей профиль — не ИТ (клиника, производство, ритейл, услуги); в вакансии перечислен зоопарк инструментов (CRM, таск-трекер, телефония, файлопомойка).
- **Possible Hypotheses:**
  - **H1 (SaaS-налог):** 8–15 подписок, растущий счёт, данные размазаны между вендорами.
  - **H2 (интеграционный ад):** инструменты есть, между ними ручной перенос данных.
  - **H3 (Alt 0, лицензионная гигиена):** уже migrating к оптимальному набору, нужен только человек на поддержку.
  - **H4 (комплаенс/безопасность):** ищут не экономию, а приватность данных на своём контуре.
- **Evidence Needed:** L1 — инвойсы SaaS (сумма и рост YoY); L2 — наблюдение переносов данных между системами; L3 — оценка часов ручной интеграции.
- **Mini Audit Angle:** инвентаризация подписок vs стоимость владения суверенным FOSS-стеком + стоимость миграции и switching cost (часто миграция дороже экономии — Via Negativa).
- **Discovery Angle:** *«Что из этого набора болит сильнее: счёт за подписки, ручной перенос между системами, или требования по данным? И считали ли стоимость переезда, если он вообще нужен?»*
- **Red Flags:** парк инструментов < 5 и счёт < $500/мес (экономии не хватит на Discovery); недавно сменили стек (болит миграция, не налог); ИТ-компания (их профиль другой).
- **Copy-Paste Trigger Note:**
> «Здравствуйте, [имя]. Заметил у вас поиск системного инженера, и в требованиях — [CRM + телефония + трекер].
> Обычно за таким набором стоит одно из: счёт за подписки растёт быстрее команды, данные между системами переносят руками, или данные нельзя держать на чужих серверах.
> Что из этого ваш случай? Если что-то из трёх — покажу, как я раскладываю стоимость владения на цифры до принятия решения.»

### Trigger #3. Internal Tooling

- **Signal:** Вакансия Full-Stack / Retool / Automation Engineer **>45 дней** или репост; формулировки «внутренние инструменты», «автоматизация процессов», «скрипты для отдела».
- **Possible Hypotheses:**
  - **H1 (костыльный конвейер):** бизнес пытается кодом лечить процесс, который чинится регламентом или готовым инструментом.
  - **H2 (найм не идёт):** вакансия нереалистична (зарплата vs требования), внутренний разраб — костыль найма.
  - **H3 (Alt 0, валидный продукт-интернал):** у компании реальная специфика, и внутренний тул — правильное решение.
  - **H4 (протухший интранет):** старый самописный тул разваливается, ищут того, кто похоронит и перепишет.
- **Evidence Needed:** L1 — репозиторий/таск-трекер внутренних тулов (возраст, активность); L2 — наблюдение процесса, который «автоматизируют»; L3 — интервью с заказчиком автоматизации.
- **Mini Audit Angle:** Hierarchy of Interventions (Level 0–3) по процессу: чаще всего Level 1 (SOP) убивает 80% запрошенной «автоматизации». Blindfold Test обязателен.
- **Discovery Angle:** *«Какой процесс пытаются автоматизировать — и сколько раз он уже переписывался? Что сломалось в предыдущей попытке?»*
- **Red Flags:** компания — продуктовая ИТ (у них это основной процесс, всё законно); вакансия закрыта быстро (проблемы нет); ноль артефактов предыдущих попыток (значит, боли может не быть).
- **Copy-Paste Trigger Note:**
> «Здравствуйте, [имя]. У вас второй месяц открыта вакансия на внутренние инструменты ([источник]).
> В большинстве случаев за этим стоит одно из: процесс, который пытаются автоматизировать, не описан и каждый раз другой; зарплата в вакансии не сходится с требованиями; или предыдущий самописный тул развалился.
> Какой вариант ваш? Если процесс «плывёт» — это чинится без единой строчки кода, и я покажу как на вашей ситуации.»

### Trigger #4. Reposted Head of Ops

- **Signal:** Вакансия COO / Head of Operations / Ops Lead перезапущена (та же компания, 2-й–3-й круг), либо открыта >60 дней; в тексте — «навести порядок», «выстроить процессы с нуля».
- **Possible Hypotheses:**
  - **H1 (хаос процессов):** никто не может систематизировать операции, каждый финалист сливается.
  - **H2 (срыв онбординга):** люди приходят и уходят — процесс незакрепляем, ноют процессы, а не люди.
  - **H3 (бюджет/власть):** позиция номинальная — ищут «руки», а полномочий менять не дадут.
  - **H4 (Alt 0, редкий профиль):** роль нишевая, просто рынок пустой.
- **Evidence Needed:** L3 — интервью с финалистами/командой (что именно не срослось); L1 — артефакты процессов (регламенты, трекеры — есть/нет); L4 — история вакансии и отзывы сотрудников.
- **Mini Audit Angle:** оффер Fractional Discovery на 1–2 недели до найма: оцифровать регламенты и снять рутину, чтобы финалист вышел в готовую систему. Change Capacity — обязательный замер (по кейсу ERMAK: система без готовности к изменениям не приживается).
- **Discovery Angle:** *«Сколько человек уже было на этой роли и что каждый не успел? Если третий финалист уйдёт так же — что изменится?»*
- **Red Flags:** полномочий у роли нет и не планируется (я продам диагностику в стену); владелец считает, что проблема в кандидатах (Alt: политический саботаж — не чинится аудитом); ноль бюджета на позицию заморожен.
- **Copy-Paste Trigger Note:**
> «Здравствуйте, [имя]. Заметил, что вакансия руководителя операций у вас открыта повторно ([срок]).
> Обычно это означает одно из трёх: процессы не формализованы и их нечем передать, каждый новый руководитель не получает полномочий, или профиль роли просто редкий на рынке.
> Сколько человек уже было на позиции? Если финалисты сходят с дистанции — есть формат 2-недельной диагностики, которая готовит систему до выхода человека, а не после.»

### Trigger #5. Clinic / Salon Scale

- **Signal:** Открытие нового филиала / второй точки: новости компании, вакансии массово по локации №2, ремонт/аренда (OSINT L4–L5).
- **Possible Hypotheses:**
  - **H1 (немасштабируемая координация):** запись и графики живут в ручном журнале/чате — второй филиал удвоит ручную работу.
  - **H2 (Alt 0, готовая франшиза-модель):** процессы уже отработаны на первой точке, масштаб идёт чисто.
  - **H3 (кадровый разрыв):** проблему видят в найме персонала, а не в координации.
- **Evidence Needed:** L1 — как ведётся запись на точке №1 (логи/журнал); L2 — shadowing дня администратора; L3 — интервью с управляющей первой точки.
- **Mini Audit Angle:** стресс-тест процесса точки №1 на ×2 нагрузки до открытия филиала + расчёт накладных расходов координации на два контура.
- **Discovery Angle:** *«Что происходит с записью и графиками первой точки, когда администратор уходит на обед/болеет? Вторая точка это умножит на два.»*
- **Red Flags:** франшизная/сетевая модель уже формализована (H2 подтверждается); первая точка работает < 6 месяцев (нечего масштабировать); открытие — фикция для отчётности.
- **Copy-Paste Trigger Note:**
> «Поздравляю с новой локацией, [имя] — увидел [источник новости].
> Обычно в этот момент одно из двух: процессы первой точки уже упакованы и вторая просто повторяет их, или запись/графики живут в журнале и чатах — и вторая точка удвоит ручную работу.
> Как у вас? Если второе — есть быстрый способ посчитать, во что это выльется за квартал, до открытия.»

### Trigger #6. RevOps Signal

- **Signal:** Вакансии RevOps / Sales Ops / Revenue Operations / Business Analyst; жалобы на «нет прозрачности по воронке», внедрение 2-й CRM при живой 1-й.
- **Possible Hypotheses:**
  - **H1 (потеря видимости воронки):** данные о сделках размазаны между CRM, чатами и таблицами; отчёты собираются вручную.
  - **H2 (CRM-протез):** CRM есть, но не отражает реальный процесс — менеджеры ведут сделку в чатах, в CRM заносят для отчёта.
  - **H3 (Alt 0, нормальный рост штата):** компания просто выросла, роль нужна для зрелости.
- **Evidence Needed:** L1 — длина сделки и конверсия из CRM vs фактические счета; L2 — наблюдение работы менеджера (где реально живёт сделка); L3 — интервью с продажами.
- **Mini Audit Angle:** карта «где реально живёт сделка» vs где она должна жить; расчёт стоимости ручной отчётности (часы × ставка ревизора).
- **Discovery Angle:** *«Если попросить у вас воронку за прошлый квартал — сколько часов и чьих рук это займёт? И совпадает ли она с реальными счетами?»*
- **Red Flags:** команда продаж < 3 человек (рано); CRM внедрили < 3 месяцев назад (не устоялась); роль дублирует уже работающего аналитика.
- **Copy-Paste Trigger Note:**
> «Здравствуйте, [имя]. Вижу у вас поиск RevOps / Sales Ops ([источник]).
> За такой ролью обычно стоит одно из: воронку видно только вручную (сборка отчёта — отдельный труд), CRM есть, но сделки реально живут в чатах, или просто выросли и пора наводить зрелость.
> Что из этого ближе? Если первое или второе — могу показать, как я за 2 недели снимаю фактическую картину по логам, а не по опросам.»

### Trigger #7. PM Explosion

- **Signal:** В компании несколько одновременных вакансий/сотрудников Project Manager / Delivery Manager / Coordinator; доля «координаторов» в структуре заметно растёт (LinkedIn/сайт команды).
- **Possible Hypotheses:**
  - **H1 (координация вместо системы):** согласования живут в людях, каждый новый проект = новый координатор.
  - **H2 (перекладывание бюджета):** PM нанимают вместо исправления сломанного процесса交付а.
  - **H3 (Alt 0, матричный рост):** много параллельных проектов у каждого клиента — координаторы законны.
- **Evidence Needed:** L1 — количество активных пересечений людей/проектов (трекер); L2 — наблюдение дня координатора (доля времени на «проталкивание»); L3 — интервью с исполнителями (что блокирует).
- **Mini Audit Angle:** карта согласований (кто кого ждёт) + подсчёт «налога координации» на проект; проверка, сводится ли боль к отсутствию одного общего трекера/регламента.
- **Discovery Angle:** *«Сколько человек в компании тратят время на то, чтобы «дожать» другие отделы? Что происходит, когда координатор в отпуске?»*
- **Red Flags:** строительно-монтажные/событийные отрасли, где координаторы — суть бизнеса (H3); компания < 15 человек (рано); PM-вакансии — это ротация уволившихся, а не рост.
- **Copy-Paste Trigger Note:**
> «Здравствуйте, [имя]. Обратил внимание — у вас открыто несколько ролей PM/координатора одновременно ([источник]).
> Часто это значит одно из: согласования живут в людях и каждый новый проект требует нового координатора, PM нанимают вместо починки процесса, или проектов реально много и это законная матрица.
> Какой у вас случай? Если согласования в людях — покажу, как за 15 минут прикинуть, во сколько такой «налог» обходится за год.»

### Trigger #8. Devs Do Support

- **Signal:** Вакансия Support Lead / Customer Success Manager при том, что поддержка де-факто идёт через разработчиков (в вакансии — «работа с багами», «связь с командой разработки»); или в профиле команды CSM нет, а поддержка идёт в общем чате.
- **Possible Hypotheses:**
  - **H1 (разработка делает саппорт):** продукты без слоя поддержки — разработчики тушат пожары вместо фич.
  - **H2 (саппорт не удерживает):** поддержка есть, но отток клиентов — хотят CSM, чтобы спасать аккаунты.
  - **H3 (Alt 0, продуктовая зрелость):** компания выросла из «все всё делают» и формализует роль.
- **Evidence Needed:** L1 — распределение времени разработчиков (трекер/история PR vs тикеты); L2 — наблюдение разбор одного инцидента; L3 — интервью с разработкой.
- **Mini Audit Angle:** расчёт стоимости часа разработки vs часа поддержки на типовой тикет; карта «кто тушит какие пожары»; приоритезация: SOP/сервис-деск → готовые хелпдески → кастом.
- **Discovery Angle:** *«Что происходит с багом, о котором написал клиент в пятницу вечером? Кто его поднимает в понедельник и сколько это стоит по часам?»*
- **Red Flags:** B2C-массовый продукт (там своя экономика поддержки); поддержка — ядро продукта (аутсорс-хелпдеск, всё законно); найм уже закрыт.
- **Copy-Paste Trigger Note:**
> «Здравствуйте, [имя]. У вас открыта позиция Support Lead / CSM ([источник]).
> Обычно за этим стоит одно из: клиенты пишут прямо разработчикам и те тушат баги вместо фич, поддержка есть, но аккаунты утекают, или просто пришло время формализовать роль.
> Какой сценарий ваш? Если первый — могу показать, как посчитать, сколько часов разработки уходит в «не-разработку» за месяц.»

### Trigger #9. AI Engineer in a Non-AI Company

- **Signal:** Вакансия AI Engineer / Automation Engineer / AI Specialist в компании, чей бизнес — не ИИ (логистика, производство, услуги, ритейл).
- **Possible Hypotheses:**
  - **H1 (лечат организацию кодом):** процессная боль упакована в «нам нужен AI», потому что так проще продать бюджет.
  - **H2 (FOMO-директива):** сверху сказано «внедрите AI» — ищут того, кто переварит пустое ТЗ.
  - **H3 (валидный узкий кейс):** есть конкретный процесс (разбор документов, классификация заявок), где ML реально окупается.
  - **H4 (Alt 0, подготовка к раунду):** AI в вакансии — косметика для инвесторов.
- **Evidence Needed:** L3 — интервью: какой процесс хотят «AI-шить» и как он работает сейчас; L1 — объём/формат данных под кейс; L4 — контекст компании (раунд, пресс-релизы).
- **Mini Audit Angle:** Via Negativa к AI: сначала Hierarchy of Interventions — если процесс не описан, ни один AI его не спасёт (кейс ERMAK: Change Capacity 2/5 + Founder Bottleneck — софт запрещён). Если кейс валиден — расчёт окупаемости против простого SOP.
- **Discovery Angle:** *«Какой процесс хотите отдать AI — и что с ним сейчас не так, если убрать слово AI из вопроса?»*
- **Red Flags:** нет владельца процесса и измеримой боли (чистый H2); бюджет выделен под «тему года» без критериев успеха; компания не может дать ни одного примера данных.
- **Copy-Paste Trigger Note:**
> «Здравствуйте, [имя]. Заметил у вас поиск AI / Automation Engineer — при том, что бизнес у вас в [отрасль].
> Обычно это одно из: есть конкретный рутинный процесс, который реально можно отдать машине; сверху пришла директива «внедрите AI», и ТЗ пока пустое; или процесс болит сам по себе, а «AI» — просто способ получить бюджет.
> Что из этого ваш случай? Если первые два — покажу, как я за 2 недели проверяю, окупится ли вообще что-то строить, до найма инженера.»

### Trigger #10. Fractional Replacement

- **Signal:** Вакансия COO / Operations Manager / Business Process Manager с зарплатой, которую SMB тянет с болью, или вакансия висит месяцами из-за бюджета.
- **Possible Hypotheses:**
  - **H1 (дорогой человек для дешёвой боли):** 80% работы этой роли — оцифровка и упаковка процессов, что делается за 2 недели, а не наймом на $X k/год.
  - **H2 (реальная управленческая дыра):** роль действительно нужна постоянно, вопросы не в процессах, а в управлении.
  - **H3 (Alt 0, founder-экспансия):** фаундер освобождает себя для роста — роль законна.
- **Evidence Needed:** L3 — интервью: что именно должен сделать этот человек за первые 90 дней; L1 — есть ли уже хоть какие-то артефакты процессов.
- **Mini Audit Angle:** прямая альтернатива: SpecKit Discovery за $350–490 vs найм на $5–15k/мес. Если 90-дневный план роли = «навести порядок в X, Y, Z» — это ровно скоуп Discovery.
- **Discovery Angle:** *«Если этот человек придёт — что он должен сделать за первые 90 дней, чтобы вы сказали, что наняли его не зря?»*
- **Red Flags:** 90-дневный план = «управлять людьми» (не оцифровка — мне нечего продать, и это честно); вакансия — HR-формальность; ноль бюджетной независимости у инициатора найма.
- **Copy-Paste Trigger Note:**
> «Здравствуйте, [имя]. Вижу поиск Operations Manager / COO ([источник, срок]).
> Не буду предлагать себя на роль — вопрос другой: что этот человек должен успеть за первые 90 дней? В 8 из 10 вакансий ответ — «описать и упаковать процессы в X и Y», и это делается за 2 недели как диагностика, без найма на постоянную ставку.
> Что у вас в планах на роль? Если 90-дневный план — про процессы, покажу, как это выглядит в формате 2-недельной оцифровки.»

### Trigger #11. Migration Churn

- **Signal:** Компания мигрирует с платформы (посты «мы переезжаем с X на Y», вакансии «специалист по миграции из Zendesk/AmoCRM/1С», публичные скрины выбора инструмента).
- **Possible Hypotheses:**
  - **H1 (недооценённый switching cost):** переезд затягивается, данные теряются, команда сидит на двух системах параллельно.
  - **H2 (миграция как дымовая завеса):** инструмент меняют вместо исправления процесса (в новой системе всё повторится).
  - **H3 (Alt 0, плановая замена):** вендор подорожал/умер, миграция чисто техническая и идёт по графику.
- **Evidence Needed:** L1 — параллельная работа двух систем (двойной ввод, расхождения данных); L3 — интервью: какие критерии успеха миграции и кто их проверяет.
- **Mini Audit Angle:** проверка гипотезы «проблема в инструменте или в процессе» до того, как миграция зацементирует старые грабли в новом месте. Ретро-цена двойного ввода за период.
- **Discovery Angle:** *«Что вы будете делать по-другому в новой системе, чтобы не воспроизвести те же грабли? Если ответ «ничего» — миграция просто перенесёт боль.»*
- **Red Flags:** миграция под контролем интегратора и идёт по плану (H3); процесс в новой системе описан (H2 снята); контракт со старым вендором уже расторгнут (поздно).
- **Copy-Paste Trigger Note:**
> «Здравствуйте, [имя]. Увидел, что вы переезжаете с [система] на [система] ([источник]).
> На этом этапе обычно одно из: переезд технический и идёт по графику, параллельно болит двойной ввод и расхождения данных, или в новой системе тихо воспроизводится тот же процесс, что и в старой.
> Как у вас? Если второе или третье — есть 2-недельный чек перед зацементированием: снимаем процесс до миграции, а не после.»

### Trigger #12. Vacancy Silent Kill

- **Signal:** Вакансия закрыта/удалена после 60+ дней **без** анонса найма; или поиск «заморожен и перезапущен» 2+ раза; в компании тишина по этой роли в соцсетях.
- **Possible Hypotheses:**
  - **H1 (бюджет умер, боль осталась):** нанять не смогли/не дали денег, проблему костылят вручную прямо сейчас.
  - **H2 (нашли дешёвый костыль):** закрыли фрилансером/стажёром/скриптом — работает плохо, но терпят.
  - **H3 (Alt 0, боль решена):** процесс починили, роль не нужна.
- **Evidence Needed:** L4 — история вакансии (скрины, архив, Wayback); L3 — косвенный вопрос в касании (ниже); L1 — только после ответа (логи/наблюдение).
- **Mini Audit Angle:** самый «тёплый» триггер: боль подтверждена самим фактом незакрытой вакансии, но бюджет под неё, возможно, умер — значит, дешёвый вход (Discovery) может быть единственным, что они могут себе позволить.
- **Discovery Angle:** *«Вы искали человека на [роль] и потом поиск исчез — нашли, заморозили или решили по-другому? Если заморозили — что случилось с самой задачей?»*
- **Red Flags:** H3 подтверждается в первом ответе (боль снята — честно отпускаем); вакансия снята из-за продажи/слияния компании; инициатор поиска уволился.
- **Copy-Paste Trigger Note:**
> «Здравствуйте, [имя]. Помню, у вас в [месяц] была вакансия на [роль] — сейчас её уже не видно.
> Обычно в этот момент одно из: наняли и всё работает, поиск заморозили, а задачу костылят вручную, или боль сняли другим способом.
> Как в итоге вышло? Если задачу всё ещё закрывают руками — скажу честно, есть решение дешевле найма, и покажу на цифрах, стоит ли оно того.»

### Trigger #13. New Executive (Job Change)

- **Signal:** Смена роли: новый COO / Head of Operations / VP Sales / RevOps / Director of Delivery в целевой компании. Источник: Sales Navigator **Job Changes** (алерты по сохранённым лидам и ролям), объявления LinkedIn. **Отличие от вакансий:** здесь человек уже внутри и с бюджетом — это сигнал предложения, а не спроса.
- **Почему это самый сильный тип сигнала:** новый руководитель получает одновременно **бюджет + мандат на изменения + желание показать результат быстро**. Окно изменений — первые 30–90 дней в роли.
- **Possible Hypotheses:**
  - **H1 (quick wins):** новому руководителю нужны видимые результаты за первый квартал — оцифровка и упаковка процессов идеальный «первый успех» для отчёта наверх.
  - **H2 (привезённый playbook):** человек тащит процессы с прошлой работы и всё уже расписано — ей нужна реализация, не диагностика.
  - **H3 (ротация без мандата):** просто замена ушедшего, никаких полномочий на изменения не дали.
  - **H4 (Alt 0, плановый переход):** преемник готовился полгода, всё стабильно.
- **Evidence Needed:** L4 — объявление о назначении, посты новичка о планах (что обещает менять); L3 — первый разговор (см. Discovery Angle); L1 — только после ответа.
- **Mini Audit Angle:** вход через 3–6 недель после вступления в роль (не день первый — человек ещё читает, не через год — окно закрыто). Discovery подаётся как «быстрая победа к квартальному отчёту»: 2 недели — карта засоров и регламенты, у руководителя на руках готовый результат.
- **Discovery Angle:** *«Вы теперь отвечаете за [область] — что первое обещали исправить наверху? И что из этого реально можно показать цифрами за квартал?»*
- **Red Flags:** H3 подтверждается (нет мандата — я продам диагностику в стену); новичок принёс готовую систему и вендора с прошлого места; компания в продажах/слиянии; человек вступил < 2 недель назад (рано) или > 6 месяцев назад (поздно).
- **Copy-Paste Trigger Note:**
> «Здравствуйте, [имя], поздравляю с новой ролью — увидел назначение в [компания].
> У руководителей операций в первые месяцы обычно одна из двух задач: быстро показать измеримый результат наверху, или привезти и приживить систему с прошлого места.
> Что у вас? Если первое — есть формат 2-недельной диагностики, который к концу квартала даёт карту процессов и цифры, не требуя найма команды. Просто спросить, актуально ли?»

## 📊 Raw Touch Log (Полевая Статистика)

Каждое касание = одна строка плоского лога. Агрегат — производная от лога, не самостоятельная таблица (два источника дрифуют — остаётся один).

**Операционный лог живёт в:** [`undreplans/docs/projects/underundre/outreach-touch-log.md`](../../../undreplans/docs/projects/underundre/outreach-touch-log.md)

### Формат строки (заполнение ≤ 30 секунд, иначе лог умрёт)

```csv
Date,Company,Trigger,Channel,Reply,Call,Discovery,Proposal,Won,Lost,Reason
2026-11-05,Клиника N,01-wa-trap,LinkedIn,2026-11-07,2026-11-12,,,,,NO_BUDGET
2026-11-06,Salon M,01-wa-trap,Email,,,,,,,,,NO_REPLY
```

- **Чекпоинты (Reply → Call → Discovery → Proposal → Won/Lost):** проставляется **дата прохождения**; пусто = не дошёл.
- **Channel:** LinkedIn / Email / TG — без этого Reply % нельзя интерпретировать (в LinkedIn он ниже по определению).
- **Reason** заполняется только при Lost — код из таксономии ниже. Это главный обучающий столбец пака.

### Таксономия причин потери (Reason)

| Код | Смысл | Что это говорит о паке |
| :--- | :--- | :--- |
| `NO_REPLY` | Молчание 7+ дней | Крючок не попал (или канал мёртвый) |
| `NO_PAIN` | Ответили: «проблемы нет» | Гипотеза гнилая — триггер в ремонт |
| `NO_BUDGET` | Боль есть, денег нет | Триггер живой, сегмент бедный |
| `NO_AUTHORITY` | Говорил не с P&L-байером | Ошибка таргета, не триггера |
| `LOST_STATUS_QUO` | «Решили ничего не менять» | Change Capacity провален до старта |
| `BAD_FIT` | Не мой профиль вообще | Мусорный таргет, чистить лист |
| `PRICE` | Дорого для трипваера $350–490 | Сигнал для бизнеса-плана, не для пака |
| `COMPETITOR` | Ушли к другому/внутрь | Логируем кто — пригодится |

### Агрегация (раз в месяц, при ревизии пака — 5 минут руками или любой spreadsheet)

```csv
Trigger,   Sent,Replies,Reply%,Calls,Call%,Discovery,Discovery%,Won,Lost
01-wa-trap,  15,    4,   27%,   2,   50%,     1,       25%,     0,  1
03-internal, 10,    5,   50%,   4,   80%,     2,       50%,     1,  1
```

Конверсии считаются каскадно: Reply % = Replies/Sent; Call % = Calls/Replies; Discovery % = Discovery/Calls. Close % = Won/Sent.

### Правила ревизии (Principle XIII в действии)

1. **Норма выборки:** вердикты по триггеру — только после **30–50 касаний**. До этого — никаких выводов «это золото/мусор».
2. **Триггер оценивается по двум точкам минимум:** Reply % (крючок работает?) и Discovery % (боль реальна?).
3. **Хвост на выброс:** нижний квартиль по Reply % после нормы выборки — заметки переписываются с нуля (гипотезы мимо, не сигнал).
4. **Хвост на тираж:** верхний квартиль — свернуть в шаблон, найти такие же сигналы в 2× большем объёме.
5. **Ложный позитив:** высокий Reply % + нулевой Discovery % = крючок острый, гипотеза гнилая. Переработать Possible Hypotheses, не крючок.
6. **Разбивка по Reason важнее разбивки по триггерам:** если #1 умирает от `NO_BUDGET`, а #3 от `NO_PAIN` — это два разных ремонта.
7. **Ревизия пака:** не чаще раза в месяц и только по цифрам лога. Новые триггеры добавляются только если рынок показал дырку, а не кабинетная идея.

## 🧰 Tool Ladder (лестница инструментов — гейтами, не желанием)

**Принцип:** строим систему поиска **сигналов**, не «AI-систему поиска клиентов». Подписка покупается, когда текущий контур физически перестал вместить объём — по логам, а не по предвкушению.

| Stage | Стек | Что делаем | Гейт перехода (вперёд — только при его закрытии) |
| :--- | :--- | :--- | :--- |
| **0 (сейчас)** | **Sales Navigator** + плоский лог `outreach-touch-log.md` | Saved searches по вакансиям + **Job Changes алерты** (роли COO/Ops/RevOps/VP Sales); ручные касания по карточкам пака; Reason-коды в логе | 20–30 лидов в логе **и** 1–2 триггера стабильно дают Reply ≥ 30% |
| **1** | **+ Clay** (обогащение и персонализация) | Массовое обогащение листа (сотрудники, свежие посты, сигналы) вместо ручного гугления; касания всё ещё пишутся руками | 3–5 платных клиентов (Discovery ✓ → Paid ✓) |
| **2** | **+ Apollo / CRM / автоматизация** | Пайплайн в CRM, авто-дедлайны по фоллоу-апам, отчётность вместо CSV | Не ниже 10-sale Demand Gate; не открывать раньше |

**Anti-patterns (стоп-сигналы):**

- Покупка Clay/Apollo **до** 20–30 лидов в логе = покупка инструментов вместо поиска сигналов.
- Свой скрипт-парсер вакансий / AI-скринер **до** первых 3 платных клиентов = кабинетное ресерч-удовольствие по Принципу XIII.
- Любой новый инструмент покупается на **один месяц** с решением по логу: дал ли он прирост Reply % или только красивый дашборд.
