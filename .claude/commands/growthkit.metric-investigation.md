## Goal

Сгенерировать доказательный диагностический меморандум расследования аномалии продуктовой/бизнес метрики B2B-оператора (**Metric Forensic Investigation Memo**).
Работать в гибридной роли: **Senior Growth Analyst**, **Quantitative Forensic Investigator** и **B2B Growth Strategist**.

Главная цель:
**Не «нагенерировать гипотез роста», а методом исключения (Via Negativa) локализовать истинную причину просадки или аномалии метрики, отделить корреляцию от причинности и выдать недвусмысленные указания: что чинить в операциях (Run), а что отдавать в разработку платформы (Change).**

## Ключевые аналитические инварианты (Core Invariants)

### 1. MECE-декомпозиция воронки и выручки (Zero Synthetic Leaks)

Запрещено исследовать метрику изолированно. Любая аномалия раскладывается по физическому уравнению воронки:

- **Уравнение оборота и вала:**  
  `GGR = Turnover × (1 - RTP) = Active Bettors × Bets/User × Avg Bet × House Edge`
- **Уравнение чистой выручки:**  
  `NGR = GGR - Bonus Costs - Direct Taxes/Royalties - Payment/Admin Fees`
- **Конверсионная труба пользователя:**  
  `Traffic → Registration (CR1) → FTD (CR2) → Repeat Deposit (CR3) → Retention_D(X) / Churn / Reactivation`

### 2. Дихотомия Run vs. Change (Обязательное разделение действий)

Каждая рекомендация обязана иметь строгую классификацию:

- **RUN (Операционный рычаг):** Действие в рамках текущего функционала платформы (корректировка вейджера бонуса, сегментация рассылки в CRM, перенастройка лимитов ставок оператором, переключение приоритета платежного шлюза через админку). Адресат: **Account Management / Оператор**.
- **CHANGE (Продуктово-инженерное изменение):** Необходимость доработки кода платформы (рефакторинг формы регистрации, устранение бага в API провайдера игр, разработка нового платежного метода, изменение логики начисления кешбэка). Адресат: **Product Team / Discovery Sprint**.

### 3. Защита от парадокса Симпсона и ложной корреляции

- Агрегированные данные скрывают правду. Запрещено делать выводы по общей динамике без сегментации минимум по двум осям: **GEO / Источник трафика / Когорта по дате первого депозита (FTD) / Тип устройства**.
- Проверка волатильности малых чисел: флуктуация GGR у оператора с низким объемом активных игроков ($N < 500$) в 90% случаев объясняется дисперсией выигрышей (RTP variance), а не изменением поведения аудитории.

### 4. Реестр конкурирующих гипотез и активный поиск опровержений

Обязательный разбор конкурирующих сценариев:

- **Alt 0 (Технический/Календарный лаг):** Сезонность, праздники, задержка синхронизации данных из DWH/BI, задержка отчетов от внешнего игрового провайдера.
- **Alt 1 (Трафиковый сдвиг):** Изменение микса каналов (наплыв дешевого неконвертящего трафика, просадка ASO).
- **Alt 2 (Платежный засор):** Деградация Success Rate конкретного платежного метода (PSP), ошибки 3D-Secure.
- **Alt 3 (Эрозия монетизации / Бонус-абьюз):** Рост вымывания маржи через неэффективные промокампании или фрод.
- **Alt 4 (Продуктовый дефект):** Релизный баг, рост ошибок API, деградация скорости загрузки лобби.
- **H₀ (Нулевая гипотеза):** Статистический шум в пределах допустимого доверительного интервала ($\pm 2\sigma$).

4. **Продуктовое действие (CHANGE):** Что передано в бэклог платформы (если применимо).
5. **Ожидаемый эффект:** Измеримый возврат метрики к целевому коридору.

## 3. Competing Hypotheses Register & Via Negativa Elimination

| Гипотеза | Механизм влияния | Проверяемая метрика / SQL-запрос | Статус | Доказательство исключения (Disconfirming Evidence) |
| :--- | :--- | :--- | :---: | :--- |
| **Alt 0 (Календарь/Лаг)** | Ошибки синхронизации DWH | Сверка сырых транзакций с логами провайдера | ❌ KILLED | Данные синхронизированы 1:1, лагов нет |
| **Alt 1 (Качество трафика)** | Наплыв нецелевого трафика | Регистрации выросли, FTD упал | ❌ KILLED | Объем регистраций стабилен, источник не менялся |
| **Alt 2 (Платежный сбой)** | Отвал 3D-Secure / Лимиты PSP | Success Rate по методам депозита | ✅ CONFIRMED | Метод X показал падение успешности с 78% до 41% |
| **Alt 3 (Бонус-абьюз)** | Вымывание NGR акцией | Соотношение Bonus/NGR по сегменту | ⏸ PLAUSIBLE | Влияет как вторичный усугубляющий фактор |
| **H₀ (Статистический шум)** | Нормальная дисперсия RTP | Расчет z-score / доверительного интервала | ❌ KILLED | Отклонение превышает 3.5σ, шум исключен |

### Popperian Falsification (Критерий опровержения)
> *Подтвержденная гипотеза считается ложной, если:*  
> [Конкретное условие, например: ручной тестовый платеж через метод X проходит успешно в 10 из 10 попыток с задержкой < 3 сек].

## 4. Run vs. Change Action Matrix

### 4.1. Вектор RUN (Оперативные действия для Account Management)
*Действия, не требующие релиза кода, запускаемые за 24 часа:*
1. **Перенаправление трафика / каскад платежек:** В админке оператора выставить приоритет на резервный платежный шлюз Y.
2. **Коммуникация с оператором (BLUF-скрипт):** «У оператора Z зафиксировано падение FTD на 14% из-за просадки шлюза X в конкретном GEO. Рекомендуем активировать альтернативный метод и отправить пуш-уведомление отвалившимся пользователям».
3. **Калибровка промо:** Временно отключить акцию А для сегмента с нулевым LTV.

### 4.2. Вектор CHANGE (Продуктовые доработки платформы)
*Задачи для передачи в Product Discovery / Engineering:*
1. **Архитектурный предохранитель:** Разработка механизма автоматического переключения каскада при падении Success Rate шлюза ниже 60% (Auto-Failover).
2. **UI/UX оптимизация:** Вывод информационного баннера в кассе при временной недоступности метода оплаты.
